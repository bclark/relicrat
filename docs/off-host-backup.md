# Manual encrypted off-host recovery copy

The first off-host recovery copy is stored on the operator's Mac, outside
Technodrome. It protects against losing the worker/NAS while the Mac and its
recovery key remain available. It is not off-site storage, scheduled backup,
retention management or production disaster recovery. Continue using synthetic
records until the remaining recovery/deployment requirements are verified.

This procedure composes existing tools: `scripts/backup.py`, Docker image export,
Git source export, ordinary SSH, and OpenSSL CMS. No backup service, cloud account,
new application dependency or custom cryptography is introduced.

## Recovery contents

A capsule contains exactly:

- `backup/database.dump`, `backup/media.tar`, `backup/state.json`, and
  `backup/manifest.json`, produced by the existing offline capture command;
- `images.tar.gz`, containing the exact API, PostgreSQL and web image IDs;
- `image-ids.json`, mapping those three service names to their actual image IDs;
- `source.tar`, exported from the exact reviewed Git commit for that release;
- `capsule.json`, format 1, recording that source commit and the SHA256 of each
  preceding file, with `owner_credentials_included: false`.

Container images are needed because the original restore command requires the
exact image IDs to exist. A database/media copy alone is insufficient after
image-cache loss. The web image and reviewed source permit a later controlled
promotion as well as the offline database/media verification. Keep Linux/amd64
images on a compatible replacement Docker host.

Exclude `.env.owner`, Compose environment files, SSH keys, GitHub/Codex tokens,
and private decryption keys. Source must come from `git archive`, not an entire
working directory. Backups do contain session hashes and collection metadata;
treat both encrypted artifacts and temporary plaintext as private.

## Key custody

On the Mac, keep encrypted archives in a dedicated mode-0700 directory outside
Git and keys in a separate mode-0700 configuration directory. Use a restrictive
`umask 077` for all generated files. The operator's local record identifies the
actual paths. Never overwrite an existing key pair.

For a new recipient only, OpenSSL can create the key/certificate without printing
private material. Substitute private paths and first confirm both files are absent:

```sh
umask 077
openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 -nodes \
  -keyout /PRIVATE/KEYS/recipient-key.pem \
  -out /PRIVATE/KEYS/recipient-cert.pem \
  -subj '/CN=RelicRat offline recovery'
```

The certificate is public and selects the encryption recipient. The private key
is unencrypted on the Mac, protected by its file/directory permissions; this is
not a claim that the Mac's disk encryption is enabled. It never needs to be placed
on the NAS. Losing the key makes encrypted archives unrecoverable. Before relying
on real data, preserve a separate protected recovery-key copy and test access to
it. Copying the encrypted archive without the key is appropriate for later off-site
storage; do not synchronize the private-key directory with the archives.

## Repeat a capture

1. Identify the actual running project's trusted Compose file, image IDs, source
   commit and named data volumes. Use a new private capsule directory every time.
   Confirm no external writers. Never target a disposable test project by guess.
2. If Compose references owner variables, load only the private file generated by
   the trusted setup command into the **operator subprocess environment**. Do not
   print the resolved Compose model or put secret values in command arguments.
   `backup.py` has no `--env-file` option; exporting the environment before invoking
   it supplies Compose's interpolation. For example in an interactive worker shell:

   ```sh
   set -a
   . /PRIVATE/OWNER/.env.owner
   set +a
   python3 scripts/backup.py create \
     --compose /PRIVATE/RELEASE/compose.json --project EXACT_RUNNING_PROJECT \
     --offline-confirmed /PRIVATE/NEW_CAPSULE/backup
   ```

   This briefly stops the running web/API writers, fingerprints and captures all
   data, and restarts the same containers. Do not copy an incomplete capture.
3. Record actual API/db/web image IDs from `docker inspect` on those containers,
   then export all three using the worker's dedicated Docker socket:

   ```sh
   docker --host unix:///var/run/docker.sock image save \
     --output /PRIVATE/NEW_CAPSULE/images.tar API_IMAGE_ID DB_IMAGE_ID WEB_IMAGE_ID
   gzip /PRIVATE/NEW_CAPSULE/images.tar
   ```

   Record the mapping in `image-ids.json`. Do not use mutable tag names as the
   recovery identity. On a reviewed Git checkout, export the matching source:

   ```sh
   git archive --format=tar --output=source.tar EXACT_RELEASE_COMMIT
   ```

   Transfer that source archive to the capsule; do not include local configuration.
4. Finalize `capsule.json` with the exact source commit and hashes of all seven
   files. Use Python `hashlib.file_digest(..., 'sha256')` over file bytes. Refuse
   unexpected files, symlinks and pre-existing destinations. Stop modifying the
   capsule after hashing; capture another directory for subsequent changes.
5. Stream a tar of the completed capsule through the existing SSH helper into
   OpenSSL on the Mac, without an intermediate plaintext Mac archive:

   ```sh
   # Run in a shell with pipefail support, such as the Mac's zsh.
   set -o pipefail
   umask 077
   sh scripts/worker-ssh.sh 'tar -cf - -C /PRIVATE/COMPLETED_CAPSULE .' | \
     openssl cms -encrypt -binary -aes-256-gcm -stream -outform DER \
       -out /PRIVATE/ARCHIVES/NEW_CAPTURE.tar.cms.partial \
       /PRIVATE/KEYS/recipient-cert.pem
   ```

   First refuse existing output paths. Check **both** transfer and encryption exit
   status; rename the partial file to its final name only on success. The actual
   operator run uses Python subprocess status checks and fsync before rename.
   Record a SHA256 of the encrypted file. Leave failed partial artifacts private
   and clearly incomplete; never treat successful encryption alone as a verified
   recovery copy.

## Verify the copied artifact

Use the actual encrypted Mac artifact, not the original worker capture. Decrypt
into a new mode-0700 temporary directory:

```sh
umask 077
openssl cms -decrypt -binary -inform DER \
  -in /PRIVATE/ARCHIVES/CAPTURE.tar.cms \
  -inkey /PRIVATE/KEYS/recipient-key.pem \
  -recip /PRIVATE/KEYS/recipient-cert.pem \
  -out /PRIVATE/TEMP/capsule.tar
```

**Check successful authenticated decryption before inspecting or extracting its
output.** OpenSSL may write plaintext before final authentication. Never pipe
unverified plaintext directly into tar or a restore process. A failed operation's
output is unusable. AES-GCM authentication detects ciphertext changes but does
not establish who created a capsule; restore only trusted operator captures.

Inspect archive members before extraction: reject absolute paths, `..`, duplicate
names, links, devices and anything except regular files/directories. Use Python's
`tarfile` data extraction filter. Require exactly the capsule manifest and its
seven fixed members; recompute every checksum. Check that the saved image
identities match `image-ids.json`. Docker's containerd store uses OCI manifest or
index digests, while older stores may use configuration hashes: compare the right
identity and verify the referenced blob's hash, not these unlike identifiers.

Upload only the authenticated, verified `backup/` directory to a new private
worker recovery location. Run the existing restore command against it and a new
destination. This verifies all database rows, migration head, media references
and complete media checksums in fresh volumes. Keep the restored project stopped;
never start its API/web or point the live bridge at it. Remove temporary decrypted
Mac data after verification, preserving the encrypted archive and receipts.

For actual loss of the original worker, first load the saved images on a compatible
replacement engine using `docker image load --input images.tar.gz`, verify the
required IDs exist, unpack the matching reviewed source and use its `backup.py`
to restore offline. The initial test described below did **not** simulate a whole
replacement engine or load into an empty image store. Do that before claiming
complete host-loss recovery. Promotion additionally needs new owner configuration
with a **fresh session secret**, so captured sessions cannot become valid again.

## Initial verification — 2026-10-28

The operator captured the authenticated synthetic trial on merged release
`e86827727d64361b00446b8de105eb3bc51feca6`, exported all three actual image IDs
and matching source, and created a roughly 455 MiB encrypted Mac copy. Native
OpenSSL authenticated encryption/decryption and changed-ciphertext rejection
were checked on disposable bytes. The copied capsule was decrypted successfully;
every member hash and saved image identity was checked. Its recovered backup was
then uploaded into a separate location and restored to fresh offline volumes,
with the restored project retained stopped. No owner credentials were included.

An initial verification compared OCI image IDs to configuration hashes and
correctly stopped before accepting the capsule. The corrected check validates
actual OCI index/manifest descriptors and their blob digests. No archive or image
content was changed to satisfy that check.

Private receipts/logs and the runnable scoped capture/transfer/verification
operations are retained under the operator checkout's ignored
`.harness-results/off-host-backup/`. They contain local paths and are not a new
portable backup CLI. Current data remains synthetic; automation, retention,
independent off-site storage, separate key custody and an empty-image-store
replacement-host rehearsal remain outstanding.

OpenSSL's [CMS command documentation](https://docs.openssl.org/3.0/man1/openssl-cms/)
describes the encryption/decryption and streaming interface used here. This is
standard tool composition, not a custom archive-encryption protocol.
