# Collection management — visual concept

November 4, 2026. **Proposed for owner review; no application change or deployment.**

Open [the interactive concept](index.html), or serve this directory on Mac
loopback. All collections and checklist characters are fictional. Changes live
only in page memory; refresh resets them. No account, API, agent or real inventory
is accessed. A selected JSON file is read locally; the fictional example is fetched
only from this same local directory. The prompt can be copied/downloaded locally.

## Direction contract

- **Thesis:** one list for managing every collection, with the relevant next action beside each name.
- **Own world:** extend the approved RelicRat browsing/intake/editor identity: ivory, white, charcoal, burgundy, system sans, native controls. After hours uses the existing preset palette. No new tokens or brand assets.
- **Story:** manage a collection's entry fields, or start a new figure collection → describe it → take a prompt to an external agent → bring back JSON → review scope, controls and checklist → explicitly create an empty collection.
- **First viewport:** Manage collections, one Start new collection action, and one continuous list. No Collections versus My collections split. Built-in entry preferences and custom field controls expose their different existing capabilities without inventing ownership.
- **Form:** a focused extension of the established world, built as a responsive browser concept. No new visual identity or concept roll. Desktop retains collection navigation; phone stacks the same task and previews.

## Boundaries and implementation handoff

The current custom authoring contract is a **figure-collection pilot**. This
proposal does not promise arbitrary collection schemas, executable plugins,
embedded agents, ownership import, new lookup providers or automatic eligibility.
The downloadable demo prompt is abbreviated and labeled CONCEPT; implementation
must reuse the actual current schema/guidelines download rather than ship this
illustrative text.

The demo parser is deliberately not the production validator. It bounds the
preview and illustrates JSON/HTTPS errors; the server remains authoritative for
closed schema, identifiers, scope, completion, source references, limits, typed
values and ownership constraints. JSON is never executable UI. Source URLs stay
plain text and are neither fetched nor certified.

Built-in preferences choose optional entry fields, not field definitions or
provider adapters. Other's fixed basic fields are read-only in this proposal.
The existing setup also includes enabling tailored collection types and the
All-items entry default: preserve those controls in the integrated management
area during implementation; they are not replaced by this small preview.
A selected collection continues to override that default during intake.

Production review must retain the full scope/completion and source-support review from the existing authoring workflow.

Custom changes must reuse definition-preview/definition endpoints, expected
revisions, server compatibility checks, affected-collection counts and retained
history. The example's two shared names are fictional; production must display
the actual count/names it can verify, with pagination or an explicit bounded
scope if names are not all available. Do not guess shared scope from the client.
An imported independent copy must use the existing independently generated IDs.
Original-definition import must retain the existing reopen/idempotence rules.

Unknown creation retains the exact reviewed preview and safe same-preview retry.
Unknown definition/settings saves require explicit current-state inspection before
reviewing again. Do not infer success from a similarly named collection or issue a
new request identity blindly. Preserve unsaved descriptions, JSON, field drafts,
review invalidation, file-read generation guards, Cancel warnings and Back context.
No collection deletion, field removal, renaming or value conversion is proposed.
